# Requirements checklist

This checklist maps the visible Doctor Tracker project specification and the assignment email to the delivered implementation. The PDF defines product and technical requirements; the email adds the deadline, hosting, repository links, live URLs, and Reply All submission method.

**Implemented** means the requirement has source and supporting verification or documentation evidence. It does not mean public deployment has been completed. Fresh check results belong in [VALIDATION.md](VALIDATION.md). Hosting configuration alone is not evidence of a working public deployment.

The required architecture is a separate Next.js frontend, a standalone Node.js/Express backend, MongoDB, and REST communication. Backend links below point to its separate GitHub repository because `backend/` is deliberately excluded from the frontend repository.

## 6. Performance, stack, and engineering

| Requirement                                                    | Status                               | Implementation and evidence                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Optimize searching, filtering, and pagination                  | Implemented                          | Queries execute in MongoDB, return only a bounded page, and count against the same filter. Search uses normalized indexed prefixes; sorting includes an ID tie-breaker. [Query-plan evidence](https://github.com/sajeeb-ahmeed/Doctor-Tracker-API/blob/main/docs/query-plan.md) records an index scan for a selective fixture.                                                                   |
| Proper MongoDB indexing and efficient query patterns           | Implemented                          | Single-field and compound date, specialization, hospital, doctor, condition, status, and search-token indexes. Lists use lean results and populate only the returned patient page; doctor counts are aggregated rather than stored redundantly. Integration tests inspect an actual MongoDB execution plan.                                                                                      |
| Avoid unnecessary rerenders and use proper state/data fetching | Implemented                          | [React Query provider](../components/providers.tsx) owns server data with parameterized query keys, a stale interval, and explicit loading states. [Search debounce](../lib/hooks.ts) limits requests while typing. Forms keep temporary state locally. Mutations invalidate cached queries broadly, refetching active queries; more selective invalidation is a documented scaling opportunity. |
| Clean folder structure and reusable components                 | Implemented                          | App Router pages, shared UI/forms/filters, API client/types/hooks, and an Express split into configuration, lifecycle, models, validation, routes, serializers, seed, and errors. Both READMEs explain the structure.                                                                                                                                                                            |
| API validation and error handling                              | Implemented                          | Strict Zod bodies and query schemas, valid ObjectIds/calendar dates, bounded pagination, 7–15 phone digits, normalized emails, relationship checks, and consistent error envelopes. Tests cover invalid fields, duplicate emails, malformed IDs, date errors, and injection attempts.                                                                                                            |
| Separate Next.js frontend                                      | Implemented                          | [Frontend package](../package.json), [App Router pages](../app), and [Next.js configuration](../next.config.ts). All business logic remains in Express.                                                                                                                                                                                                                                          |
| Separate standalone Node.js/Express backend                    | Implemented                          | [Backend package](https://github.com/sajeeb-ahmeed/Doctor-Tracker-API/blob/main/package.json), independent repository, and [HTTP server lifecycle](https://github.com/sajeeb-ahmeed/Doctor-Tracker-API/blob/main/src/server.ts).                                                                                                                                                                 |
| MongoDB database                                               | Implemented                          | [Database connection](https://github.com/sajeeb-ahmeed/Doctor-Tracker-API/blob/main/src/database.ts), Mongoose collections, and MongoDB-backed sessions. Local development runs a real persistent MongoDB process; production requires a hosted URI.                                                                                                                                             |
| RESTful API communication                                      | Implemented                          | [Frontend API client](../lib/api.ts), same-origin API forwarding, and Express GET/POST/PATCH/DELETE endpoints with suitable status codes. The backend README documents requests, responses, and endpoint access.                                                                                                                                                                                 |
| Scalability considerations and Next.js/MongoDB best practices  | Addressed in implementation and docs | Protected server-rendered layout, server-only configuration, reusable clients/components, index-backed queries, capped pages, persistent sessions, and documented search/cache tradeoffs. Larger datasets may need cursor pagination, selective cache invalidation, or dedicated search; current fixture evidence is not a large-scale benchmark.                                                |

The evaluation criteria for code structure, query optimization, UX/UI, visualization, efficiency, authentication, and framework/database practices are supported by the evidence above. Their final qualitative assessment belongs to the evaluator; this checklist does not guarantee a score.

## Completion boundary

The documented product requirements have implementation evidence. End-to-end completion still requires public hosting, deployed acceptance checks, final live URLs/credentials, and submission through the specified email thread. See [DEPLOYMENT.md](DEPLOYMENT.md) for the acceptance sequence. Do not mark the project fully delivered solely because local tests and builds pass.
